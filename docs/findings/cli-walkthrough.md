## ステップ0: CLI の表面仕様の確認

**目的**: `--help` でサブコマンド・オプションを確認する。

### 結果1: `--help` は存在せず、いきなり本番セットアップが始まる ← 重大

`--help` を付けたにもかかわらず、ヘルプは表示されず **セットアップ本体が起動**した。
ソースで原因を確認済み（`src/index.ts` の `parseArgs`）:

- `--help` / `-h` の分岐が**存在しない**
- `-` で始まる未知の引数は**黙って無視**される
- その結果 `command` は既定値の `"setup"` のまま → `runSetup()` が走る

実際に到達した処理: 環境チェック → リリース取得 → バンドル DL/検証 → ソース固定 →
**Cloudflare 認証チェック → アカウント確定 → Step 1 のプロンプト表示**。

**つまり `--help` のつもりで叩くと、Cloudflare に認証して本番セットアップに入る。**

### 実際に存在するコマンド・オプション（ソースより）

| 種別 | 値 | 備考 |
|---|---|---|
| コマンド | `setup`（既定） / `update` | それ以外の非ハイフン引数は command として解釈される |
| オプション | `--repo-dir <path>` | 設定ファイルの読み先を指定 |
| オプション | `--from-source` | 開発用。リリースバンドルでなくクローンからビルド |
| オプション | `--repair-admin` | Admin Pages のアップロードだけ失敗した場合の復旧用 |

### 結果2: Cloudflare 認証は既存の wrangler セッションを再利用する

「Cloudflare 認証チェック中」→ **「Cloudflare 認証済み」** で通過し、ブラウザ認証は発生しなかった。
この Mac に既存の wrangler ログインがあったため。**未ログインの参加者では挙動が異なる**ので、
ステップ3 で改めて確認が必要。

> ⚠️ 通過直後に **Cloudflare アカウント ID が画面に平文表示される**。
> 手順書では「この画面のスクリーンショットを送るときは伏せる」旨を明記すること。

### 結果3: TTY が必須。パイプ入力では起動しない ← 設計上の重要事実

`</dev/null` で実行したところ、最初のプロンプトで停止した。

```
Error: TTY initialization failed: uv_tty_init returned EINVAL (invalid argument)
```

プロンプトに `@clack/prompts` を使っており、**実 TTY を要求する**。
単純な pipe による stdin 流し込みでは動かない。

## シークレットの扱い（本家 CLI の実装）

このキットの方針（`CLAUDE.md` §3.1）に直結するため記録する。

> **訂正**: 初版で「`.line-harness-config.json` にシークレットが平文保存される」と書いたが**誤り**。
> 実際に保存されるのは **`.line-harness-setup.json`（進捗ステートファイル）** で、
> しかも**成功時は削除され、失敗・中断時のみ残る**。以下が正しい。

| 項目 | 実装 |
|---|---|
| 入力時のマスキング | **無し**。`p.password` は未使用で、チャネルシークレットもアクセストークンも `p.text` で**画面に平文表示** |
| `.line-harness-setup.json`（ステート） | `SetupState` を丸ごと `JSON.stringify` するため、**`lineChannelSecret` / `lineChannelAccessToken` / `apiKey` が平文で入る**。パーミッションは既定の **0644** |
| ↑ の寿命 | **成功時**: `cleanupSuccess()` → `removeStateFile()` で**削除される**<br>**失敗・Ctrl-C 時**: `cleanupFailure()` → `saveState()` で**残る** |
| `.line-harness-config.json`（成功時に生成） | LINE のシークレット・アクセストークン・API キーは**含まれない**。プロジェクト名・各種 URL・D1/R2 名・アカウント ID など |
| git 混入対策 | ✅ `.gitignore` に両ファイルとも記載あり |
| 一時 SQL ファイル | `mode: 0o600` で作成されている |

→ **危ないのは「失敗して止まった状態」**。シークレットが 0644 のファイルで残る。
　 そしてそれは、参加者がサポートに助けを求めてファイルやスクショを送りたくなる場面と完全に一致する。
　 **#2（サポートポリシー）に「`.line-harness-setup.json` は送らないでください」を入れる必要がある。**

### API Key の一度きり問題

完了画面に API Key が表示され「**この値は再表示できません。安全な場所に保存してください**」と出る。
実際、成功時はステートファイルが消え、`.line-harness-config.json` にも含まれないため、**控え忘れると失われる**
（Worker のシークレットとして Cloudflare 側には存在するが読み出せない）。
→ 典型的な問い合わせになるので #2 / #3 で先回りする。

## 実測: Claude 経由では CLI を実行できない ← 配布方針に直結する発見

2026-09-07 確認。**Claude Code CLI と Claude Desktop の Code タブの両方で、標準入出力が TTY ではない。**

```
$ node -e "console.log(process.stdin.isTTY, process.stdout.isTTY)"
undefined undefined     ← 両環境とも同じ
```

CLI は `@clack/prompts` を使っており実 TTY を要求するため、
**Claude に実行させると最初のプロンプトで `uv_tty_init EINVAL` で落ちる。**

### 何が無効になるか

前回勉強会の `homework.md` Part 2 Step B1 は、参加者にこう指示している。

> 新しいフォルダを作って、そこで `npx create-line-harness` を実行してください。
> **対話形式で質問されるので、私が回答します**

**この手順は成立しない。** 別リポジトリ（`saniman/line-harness-workshop`）の記述なので、
本キットでは**記録に留め、修正は先方リポジトリの判断に委ねる**。

### 回避策は無い

| 案 | 可否 |
|---|---|
| `script` 等で PTY を割り当てて Claude に実行させる | ❌ PTY は確保できるが、**Claude 側から対話的に入力を送る手段がない** |
| CLI の非対話モードを使う | ❌ **存在しない**。値を渡す引数は無い（`--repo-dir` / `--from-source` / `--repair-admin` のみ） |
| 参加者が**本物のターミナル**で実行する | ✅ **これしかない** |

### 結論

**参加者はターミナル（macOS: ターミナル.app）を自分で開いて実行する必要がある。**
「コマンドを一行も打たない」という前回からの売りは、この工程では成立しない。

→ 手順書「3. セットアップツールの実行」は、**ターミナルを開く手順から書く**（C-21）。

### GUI ラッパーの評価が変わる

この制約により、GUI ラッパーの価値が当初評価より上がる。

| | Claude 経由で実行できるか |
|---|---|
| 本家 CLI を直接 | ❌ TTY が無く不可 |
| **GUI サーバーを起動** | ✅ **可能**。サーバーのバックグラウンド起動に TTY は不要で、PTY は GUI 側が握る |

つまり GUI は「ターミナルの見た目を隠す」ためのものではなく、
**Claude 主導のフローを成立させる唯一の手段**になる。投資判断はこれを踏まえてやり直す。

## 実測: Worker デプロイが cron trigger の無料枠上限で失敗（Step 10）

2026-09-07、Aki が `setup` を実行。**D1・R2 まで成功し、Worker デプロイで停止**した。

```

◆  Bot Basic ID / workers.dev サブドメイン 取得済み
◇  Worker ビルド完了
◇  Worker デプロイ失敗

wrangler deploy failed:
  This account has reached the Workers Free limit of 5 cron triggers per account.
  [code: 10072]
```

### 原因の切り分け

`apps/worker/wrangler.toml` の定義:

```toml
[triggers]
crons = ["* * * * *", "0 */6 * * *"]
```

| | |
|---|---|
| 1インストールが消費する cron | **2本** |
| Workers Free の上限 | **5本／アカウント** |
| 同一アカウントに置ける上限 | **2インストールまで**（4本）。3つ目で必ず失敗 |

Aki のアカウントは既存の Worker が cron を使っており、空きが2本未満だった。
**新規アカウントの参加者が1つ入れる分には問題ない**（2/5 で収まる）。

### この発見の位置づけ

| | |
|---|---|
| 参加者への影響 | **条件付きであり得る**。すでに Workers を使っている人、勉強会で2つ目以降を作る人、複数店舗ぶん立てたい人は踏む |
| 失敗のタイミングが遅い | **D1・R2・バケット作成が全部終わったあと**に失敗する。R2 のときと同じ「事前チェックがあれば手前で止められる」パターン |
| 復旧 | 再実行で `database` / `r2` はスキップされる（`completedSteps` に記録済み）。**再開機構の実地検証のチャンス**（★重点確認②） |

### 実測: 失敗時にシークレットが平文で残ることを確認 ← 予測どおり

想定していた **B-4 の挙動が実機で再現**した。検証中は `chmod 600` で保護した。
